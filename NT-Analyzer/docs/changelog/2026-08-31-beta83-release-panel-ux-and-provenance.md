# beta.83 — панель релиза и запрет публикации не из утверждённого main

## Что вошло

- Автообновление больше не сбрасывает раскрытые блоки, scroll и прогресс.
- Development → Canary и Canary → Production — по одному действию с живыми этапами.
- Артефакт не из утверждённого `main` нельзя опубликовать в Production.

## Решения и почему

### Обновление данных перестало быть перерисовкой страницы

Каждые 20 секунд панель переписывала свой `innerHTML`: закрывались раскрытые
блоки, терялась позиция прокрутки, экран моргал как после перезагрузки. Теперь
каркас строится один раз, поля обновляются точечно, неизменившийся блок не
переписывается вовсе, а элементы `<details>` не пересоздаются — поэтому
раскрытое остаётся раскрытым. Карточка с идущей операцией пропускается
целиком: опрос не должен подменить кнопку под курсором.

### Один переход — одно действие

Внутренние шаги перестали быть отдельными кнопками. «Отправить в Canary»
выполняет создание кандидата, сборку, проверку, развёртывание и приёмку;
«Опубликовать в Production» — подтверждение, развёртывание, readiness и smoke.
Пока идёт операция, виден текущий этап со спиннером, а кнопка заблокирована,
чтобы второй клик не запустил второй прогон. Прогресс берётся из состояния
ledger, а не рисуется по таймеру.

Приёмка Canary — настоящие запросы к живой среде: readiness, тот ли артефакт
там выполняется и отвечает ли публичная поверхность. Результат виден строкой
`✓ Readiness ✓ Artifact identity ✓ Smoke`, детали — в раскрываемом блоке.

### Артефакт из несмерженной ветки не может попасть в Production

Во время beta.82 артефакт, собранный из коммита несмерженной ветки, попал в
Canary, прошёл приёмку и оказался в одном нажатии от Production. Приёмка
говорит, что среда здорова; откуда взялся код, она не знает. Строка версии не
знает тоже — ветка несёт её так же честно.

Поэтому происхождение стало отдельным gate на backend. Кандидат пригоден для
Production, только если: ветка `main`, чистое рабочее дерево, HEAD совпадает с
`origin/main` без отставания и опережения, коммит входит в `origin/main`, и
именно этот SHA прошёл требуемый CI. Проверка стоит в `approve_production` —
после проверки `canary_passed`, чтобы здоровый Canary не мог её пронести.

Вопрос, на который ответить не удалось, считается отрицательным: если CI-статус
недоступен, публикация запрещена. Промоушен, прошедший потому, что проверку не
получилось выполнить, — ровно та поломка, ради которой этот gate существует.

Canary при этом не ограничен: собрать ветку и развернуть её для диагностики
по-прежнему можно. Запрет касается только Production.

UI решение не принимает, а отражает: панель показывает gate «Сборка сделана из
утверждённого main» с конкретной причиной отказа.

### Отправка в Canary называет, что именно собирается

Сборка и развёртывание одним кликом, без указания собираемого коммита, — то,
как артефакт ветки и попал в Canary. Действие осталось одним, но теперь оно
названо: подтверждение показывает commit, который будет собран.

| Поле | Значение |
| --- | --- |
| Candidate | `rc_e35e934fc2d74aa6b8f0170d1afd7d82` |
| Artifact | `art_edfeb143e27e4790bc851a0e61fe3410` |
| Git SHA | `03ddf47bb2e657d66d414985976448538ff99743` |
| Build ID | `sf-0.10.0-beta.83-03ddf47bb2e6-20260831T140855Z` |
| Archive SHA256 | `BE8F46427C758EEDB76A1D3D8FD2F671499051DEDFE43E3424F0258F4263FF30` |

Canary PASS → Production PASS, один и тот же artifact без пересборки.

## Прогон выполнен кнопками панели

Обе стороны цикла запущены нажатием в интерфейсе, а не backend-командой.
«Отправить в Canary» назвало собираемый commit в подтверждении и провело шесть
стадий; приёмка записала три отдельные проверки — `readiness`,
`artifact_identity`, `smoke` — и показала их строкой на карточке.
«Опубликовать в Production» провело пять стадий с блокировкой кнопки.

Дефектов нового workflow прогон не выявил. После публикации панель перешла сама:
карточка Canary сменила кнопку на «✓ Уже опубликовано в Production», карточка
Production — на «✓ Активная версия», по сравнению artifact identity, а не строки
версии.

## Инвариант проверен на настоящем случае

Артефакт `d4c7a83e`, собранный из несмерженной ветки и принятый Canary в
beta.82, к Production допущен не был: gate отклонил его по
`commit_on_origin_main`. Его заменила сборка `03ddf47b` из чистого
синхронизированного `main`, у которой все шесть условий выполнены.

## Что вскрылось при штатном запуске

`start.ps1` оставлял рабочее дерево грязным: отслеживаемый вывод рендера
governance отставал от данных на две политики из beta.80. Пока это была
неопрятность, она ничего не ломала; с появлением инварианта чистого дерева она
отключала обе кнопки панели. Догоняющий рендер закоммичен, и штатный запуск
снова оставляет `git status` чистым.
