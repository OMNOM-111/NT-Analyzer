# Виктор («Витёк») — правая рука руководителя

Карта сотрудников, аватары и ссылки на специалистов: [AGENTS.md](agents/AGENTS.md).
Технический шлюз и capability-routing: [CHIEF_AI_AGENT.md](agents/CHIEF_AI_AGENT.md).
Публичный тон: [AI_DIALOGUE_CONTRACT.md](AI_DIALOGUE_CONTRACT.md).

В интерфейсе используется официальное имя **Виктор · личный помощник и правая
рука руководителя**. Разговорное имя «Витёк» сохраняется в командах и обычном
диалоге. Виктор — личная правая рука владельца и собеседник по умолчанию для общих,
важных и межфункциональных вопросов.
Иерархия: **владелец → Витёк → Управляющий → профильные агенты и инструменты**.
`StratForge Orchestrator` остаётся названием общего интерфейса и единого шлюза,
как и в прежней версии приложения. В автоматическом режиме отвечает Витёк;
при прямом обращении владелец может вызвать Управляющего, Секретаря,
Заместителя, Марину, Толика, Никиту или Ивана, и ответ будет подписан их именем.
Orchestrator не является отдельным начальником. Витёк принимает общие результаты, отвечает за итог,
выбирает, что действительно нужно донести владельцу, и поручает Управляющему
организовать исполнение.

## Правило разговора с владельцем

Все модельные и детерминированные ветки используют один публичный контракт.
Обычный ответ занимает 1–4 коротких предложения; управленческое решение содержит
ситуацию, одну рекомендацию и при необходимости один вопрос. Обращение «Дмитрий
Сергеевич» не повторяется в соседних рабочих репликах: по умолчанию сотрудники
говорят в уважительной форме на «вы». Подробные метрики выдаются только по явному
запросу полного отчёта, а в обычном чате остаются только цифры, меняющие решение.

Автор сообщения всегда является фактическим публичным исполнителем. Виктор может
сообщить, кому делегировал работу, Управляющий координирует специалистов ниже
Виктора, а специалист докладывает только о своей части. Если запрос адресован не
тому сотруднику, ответ кратко называет передачу ответственному и остаётся в том
же диалоге. Технический `StratForge Orchestrator` никогда не подписывается как
отдельный собеседник владельца. Model/provider и ход выполнения показываются
отдельными метаданными интерфейса, но не повторяются в тексте ответа.

Любая фраза из приложения или Telegram технически проходит через единый шлюз,
и сохраняет один проверяемый маршрут ответа. Без указанного имени запрос принимает
Витёк; явное имя передаёт запрос этому участнику. Поддерживаются обращения `Виктор`, `Витёк`, `Витек`, `Витя`,
`Витька`, `Витенька`, `Vitek`, `/vitek` и `дежурный контролёр`. Ответ в общей
истории подписывается именем фактического собеседника и отправляется только один раз.

## Единый диалог приложения и Telegram

Aurora и привязанная тема Telegram — две поверхности одного диалога, а не два
независимых чата. Каноническая история определяется тройкой
`user_id + workspace_id + conversation_id`.

- входящее сообщение Telegram сначала связывается с активным аккаунтом и
  workspace отправителя, затем сохраняется в ту же историю, которую читает
  Aurora; запись в старый общий файл без scope запрещена;
- сообщение пользователя из Aurora сначала сохраняется в этой истории, затем
  зеркалируется в соответствующую тему Telegram;
- ответ сохраняется один раз с именем фактического собеседника и тем же scope,
  после чего доставляется во вторую поверхность;
- при временной ошибке Telegram реплика остаётся в долговечной очереди доставки;
  её `message_id` отличает два одинаковых по тексту сообщения и одновременно
  не допускает повторной доставки одной реплики;
- audit каждой Telegram-команды фиксирует update, отправителя, тему, входной и
  ответный message id, а также факт доставки. Ошибка доставки видна как очередь,
  а не маскируется успешным статусом.

Webhook и long-poll являются только двумя транспортами одной долговечной
`telegram.update-inbox.json`. Backend подтверждает webhook после локальной
записи, дедуплицирует точный `update_id` (не отбрасывая меньший ID, пришедший
позже), сохраняет все незавершённые элементы и держит порядок внутри темы.
Короткий reorder-буфер выбирает меньший Telegram update ID, если параллельные
webhook-доставки пришли как 102 → 101. Разные темы могут выполняться параллельно.
После трёх неуспешных попыток элемент остаётся в `dead_letter` для диагностики,
перестаёт блокировать тему, а пользователь получает короткую просьбу повторить
сообщение; недоставленное предупреждение сохраняется в reply outbox.

Старая unscoped-переписка не удаляется: она один раз сливается по `message_id`
в scoped-историю и остаётся только контрольной копией. Очистка чатов не является
способом исправления рассинхронизации и не должна уничтожать историю владельца.

Простые справки профильных агентов формируются детерминированно без вызова LLM.
Закрытый диалог сжимается в архив памяти. В начале каждого следующего модельного
запроса правила пользователя и релевантные архивы загружаются одним общим пакетом
для всех возможных исполнителей; память не выдаётся моделям по очереди и не
пересекает границы пользователя и рабочей области.

Полная проверка выполняется только при запуске Витька либо вручную по команде
`Витёк, проверь`. Между такими проверками события передаются через долговечную
очередь `data/runtime/vitek_events.jsonl`, без пятиминутного полного опроса.
Источники сигналов:

- потеря/восстановление heartbeat, изменения стратегий и свежие ошибки NinjaTrader Bridge;
- завершение, ошибка или отмена задания NinjaTrader;
- новые задачи приложения, важные новости и ценовые сигналы;
- технические сбои и отдельно предупреждения качества AI-экспериментов;
- готовность по реальному числу approved-профилей против активных portfolio slots;
- временные окна готовых стратегий и пустые промежутки биржевой сессии;
- проваленные профили, которые не были корректно скрыты в архиве;
- целостность финансового журнала и записи `needs_review`;
- просроченные задачи.

Когда владелец обращается к Виктору, GPT-5 mini в Azure Foundry используется как
быстрый смысловой диспетчер: понимает свободную речь и выбирает разрешённую
способность, но не подтверждает результат вместо приложения. Сохранённая
категория поручения имеет приоритет над новой интерпретацией модели, поэтому
финансовая задача не может превратиться в команду графика. Важная или аварийная
работа после маршрутизации получает сильнейшую доступную профильную модель.
Владелец видит имя собеседника, фактическую модель и provider, но не внутренние
ID, prompts и служебную цепочку рассуждений. Финансы
направляются Марине, стратегии и бэктесты — Толику, новости — Никите, графики —
Ивану, остальные задачи — Оркестратору. Выполняются только действия из
защищённого белого списка. Если фактического результата нет, Витёк не отмечает
задачу выполненной, а запрашивает решение владельца.
Ограничение вида `ничего не запускай` или `не изменяй` всегда трактуется как
запрет действия: слова внутри отрицания не могут стать командой запуска и не
могут заменить прямо названного собеседника другим публичным автором.

Под ответом в обоих представлениях чата показывается проверяемый ход работы:
поставлено в очередь, выполняется, ждёт решения, заблокировано либо выполнено.
Это статусы реальных действий capability/task, а не скрытые рассуждения модели.
Статус `completed` разрешён только после подтверждения целевой подсистемой:
например, восстановление NinjaTrader требует свежего heartbeat и подключённого
demo/paper-счёта. Запуск процесса, обещание агента или создание mission сами по
себе завершением поручения не являются.
Каждый финансовый отчёт явно называет выбранный период и его границы `from — to`,
чтобы месячные, годовые и all-time показатели нельзя было принять друг за друга.

Исполнение разделено на независимые агентские дорожки: один агент не получает
две пересекающиеся задачи одновременно, но разные агенты могут работать
параллельно (до шести дорожек: Витёк, Управляющий, Марина, Толик, Никита и
Иван). Главный рабочий центр находится на странице **Обзор** и показывает, кто
работает, кто свободен, план на день и неделю, важные решения и активные
поручения. Обновление этого представления не будит Виктора и не запускает полный
опрос: UI читает уже сохранённое событийное состояние. На остальных страницах
доступно действие **Поручить Виктору**, а в карточках стратегии и исследования —
контекстное **Поручить Виктору разобраться**.

Контекстное поручение всегда проходит один и тот же путь:

1. создаётся отдельный диалог Orchestrator и связанная тема Telegram;
2. сохраняется одна структурированная задача с объектом приложения, сроком,
   бюджетом и условием контроля;
3. Виктор подтверждает приём в этом диалоге, затем Управляющий назначает
   профильных исполнителей;
4. итог или единственный необходимый вопрос возвращается в тот же диалог;
5. после подтверждённого результата тема закрывается и попадает в общую память.

План на день или неделю может быть связан со стратегией, исследованием,
финансами, графиком или другим объектом, содержать комментарий владельца,
бюджет, конечное время, условие наблюдения и периодичность отчёта. Каждая цель
становится отдельной задачей, но не дублируется повторным сообщением в чат.

Внутренние инциденты сохраняются отдельно от пользовательского диалога. Витёк
не показывает owner внутренние ID, event names, severity, модели и статусы
маршрутизации. Он сообщает деловой факт, одну доказательную рекомендацию и один
конкретный вопрос. Ответ «да» или «нет» в том же диалоге запускает или отменяет
всю связанную цепочку. Для реабилитации проваленной стратегии предложение
допустимо только при сохранённой проверяемой оценке качества выше 50/100; эта
оценка не является вероятностью успеха. Иначе Витёк
рекомендует архив.

Новые инциденты сохраняются отдельно от признака доставки: если ручная
проверка создала инцидент без Telegram-отправки, фоновый цикл всё равно
доставит его позднее. При отсутствии плана Витёк один раз за локальный день и
неделю спрашивает цели, не объявляя отсутствие плана системной ошибкой.
Перед показом состояния проверяется уже записанный heartbeat Bridge. Если связь
восстановилась, старый вопрос о потере соединения и связанная задача закрываются
автоматически. StratForge **не** автозапускает `NinjaTrader.exe` и не вводит
логин NT (защита от lockout после reboot); владелец стартует NT вручную.
Запущенный NT без свежего heartbeat сам по себе не считается ложным
подтверждением восстановления.

## Фоновая работа

Запустите `00_INSTALL_VITEK_BACKGROUND.cmd` один раз. Установщик создаёт
пользовательскую задачу Windows `StratForge Vitek`, запускаемую при входе в
систему. Watchdog не открывает браузер и поддерживает backend на
`127.0.0.1:8765`. Если обычный backend уже работает, watchdog ждёт; когда он
закрывается, watchdog запускает фоновую замену.

Закрытие интерфейса не останавливает Telegram, heartbeat NinjaTrader и
событийный worker Витька. Внутренний браузер Codex по умолчанию не запускается
из-за зафиксированного 13 июля 2026 года риска; визуальный smoke допускается
только по прямому поручению владельца. Для обычной проверки используются HTTP,
DOM-контракты и стандартный Chrome. Лог находится в
`logs/vitek-background.log`. Удаление: `tools/uninstall-vitek-background.ps1`.

## Команды Telegram

- `Витёк, статус`
- `Витя, какие на сегодня задания у тебя остались?`
- `Витёк, проверь`
- `да` / `нет` после вопроса Витька
- пояснение обычным текстом после вопроса Витька
- `Витёк, отдыхай 2 часа`
- `Витёк, вернись к работе`
- `Витёк, план на сегодня: цель 1; цель 2`
- `Витёк, план на неделю: цель 1; цель 2`

Критические события отправляются и во время отдыха. Опасные торговые,
финансовые и необратимые операции не входят в полномочия Витька без отдельного
подтверждения существующего защищённого workflow.

## API

- `GET /api/vitek/status`
- `GET /api/vitek/time-windows`
- `POST /api/vitek/scan`
- `POST /api/vitek/rest`, `POST /api/vitek/resume`
- `POST /api/vitek/tasks`, `POST /api/vitek/tasks/{id}`
- `POST /api/vitek/events`
- `POST /api/vitek/plans`
- `POST /api/vitek/incidents/{id}/decision`

Состояние хранится локально в `data/operations/vitek.json`. Повторные события
объединяются по стабильному fingerprint. Пустые временные окна показываются и
анализируются, но автоматическая цепочка создания новой стратегии для них не
запускается: такую задачу владелец даёт отдельно.
