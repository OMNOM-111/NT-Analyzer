# История продукта: правило обновления

Корневая страница [`timeline.html`](../../timeline.html) — короткая визуальная передача состояния StratForge AI владельцу и следующему разработчику. При завершении **каждой задачи разработки** сверяйте её с новым фактом и обновляйте текущий пакет до закрытия задачи: функцию, исправление, приёмку или причину блокировки можно кратко записать отдельной датированной строкой в боковой панели, не раздувая карточку. При каждом подтверждённом переходе Local → Canary → Production обновляйте также снимки сред. Подробный факт и release identity по-прежнему записываются в `docs/changelog/` и release evidence; страница показывает их понятное резюме.

## Что менять

1. Проверить код, активный Local runtime и канонические current-документы. Для Canary/Production сверить Release Center, точный artifact и результаты acceptance. Если доступна только последняя запись о deploy, так и подписать снимок среды; не выдавать его за живую проверку.
2. В `timeline.html` обновить три снимка сред: версию, build/commit и состояния функций. Массив `capabilities` общий для всех сред. Номер — позиция функции в нём; порядок стабилен. Новую подтверждённую возможность добавлять **только в конец**, не переименовывая уже известные номера ради косметики. `yes` означает подтверждённое наличие, `candidate` — работу без полной приёмки, `no` — отсутствие в последнем подтверждённом выпуске. Счётчик `X/Y` считает только `yes` среди всех `Y` пунктов. Для неизвестного статуса сначала проверить источник и не рисовать ложную галочку.
3. После последнего подтверждённого серверного выпуска пополнять **одну открытую карточку поставки**: отдельные задачи в `batchTasks`, понятное название каждой, дату, статус, короткое описание и рабочую ссылку на источник. Социальную сеть, SF Chat и другие самостоятельные задачи не склеивать в одну строку. Отдельные Local коммиты и ветки не создают отдельные milestone-карточки, если относятся к этому ещё не опубликованному пакету. Чипы карточки остаются компактным резюме; детали остаются в боковой панели. Для новой milestone-карточки выбрать одну небольшую тематическую SVG-иконку из набора страницы.
4. В `progress` явно различать сохранение кода в Git, запущенную Local-сборку, сборку единого release artifact, Canary и Production. При подтверждённой Canary acceptance записать в этой же карточке точные версию, SHA, build, artifact и результат Canary. При подтверждённой Production promotion того же immutable artifact обновить Production и закрыть карточку. Если после Canary менялся код, следовать release contract и снова пройти Local → Canary; не показывать старую проверку как приёмку нового кода. Следующую открытую карточку создавать только для нового Local-пакета после закрытого выпуска.
5. Синхронно обновить затронутые current-документы, `docs/changelog/`, а при изменении состояния продукта — External GPT Context Pack. Перед Git closeout проверить JS/HTML, хронологию, номера и счётчики, статусы сред, ссылки и Light/Dark на desktop/mobile, если визуальная проверка доступна. Не менять исторические даты, версии и deployment-статусы без источника.

Карточка отвечает на три вопроса: **что сделали, где это уже доступно, что пока впереди Production**. Технические SHA, artifact и branch остаются на втором уровне. Если функция ещё `IN DEVELOPMENT`, это видно и в списке сред, и в открытом пакете.
