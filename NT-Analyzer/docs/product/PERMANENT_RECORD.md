# Постоянная запись — основополагающий принцип SF Social

> **Original ideas. Permanent history. Transparent corrections.**

**Статус:** действует в SF Chat (Development).
**Канонический источник поведения:** `app/community.py` — `PERMANENT_RECORD`,
`PERMANENT_RECORD_PRINCIPLE`, `PERMANENT_RECORD_NOTICE`, `owner_remove_content`,
`preview_owner_removal`, `owner_audit_log`, `_apply_removal`.
**Тесты:** `tests/test_community_permanence.py`, `tests/test_community.py`,
`tests/test_ux_mode.py`.

## 1. Правило для пользователя

После публикации пользователь:

- **не может удалить оригинал**;
- **не может переписать его содержание**;
- **не может изменить дату или авторство**;
- исправляет ошибку **только новой публикацией** — обычной или отдельной
  correction/follow-up, явно связанной с оригиналом.

Оригинальная запись остаётся частью истории профиля.

Правило распространяется на всех одинаково, **включая владельца платформы как
автора**. Владелец, который может незаметно убрать собственные записи, — это
ровно та задним числом наведённая чистота, против которой правило и введено.

### Зачем

Лента, из которой можно убрать неудачное и оставить удачное, ничего не говорит
о человеке — она говорит о том, что он решил показать. Постоянная запись
убирает эту возможность: под записью в SF Social нельзя замаскироваться под
бота, под чужой опыт или под версию себя, которой не было.

Ошибка в тексте, неточная мысль, изменившееся мнение — не проблема. Напишите
ещё раз. Вторая запись рядом с первой доказывает больше, чем отредактированная
первая: видно живого человека, который ошибается и справляется с этим. У
платформы есть искусственный интеллект, но ценность — в оригинальности
настоящих идей вместе с их ошибками.

### Что это значит на практике

| Действие | Результат |
| --- | --- |
| Удалить свою публикацию | Невозможно — `403` |
| Удалить свой комментарий | Невозможно — `403` |
| Удалить свою публикацию, будучи владельцем | Невозможно — `403`, то же правило |
| Изменить опубликованный текст, дату или авторство | Не существует — API редактирования нет |
| Исправить сказанное | Новая публикация; при желании — `corrects_post_id` на оригинал |
| Настроить видимость | Выбирается **до** публикации и относится к показу, а не к существованию записи |
| Удалить audit record | Невозможно — такой операции нет ни в модуле, ни в API |

### Transparent corrections

`create_social_post(..., corrects_post_id=...)` создаёт **новый объект**,
который называет исправляемую публикацию. Оригинал не меняется: у него
остаются свой текст, своя дата и своё авторство. Связь видна с обеих сторон —
`corrects_post_id` у исправления и `corrected_by_post_ids` у оригинала.
Исправить можно только собственную публикацию (`403` иначе) и только
существующую (`404` иначе).

## 2. Исключение — audited erasure

Есть требования, которые никакое продуктовое правило не отменяет: решение суда,
незаконное или опасное содержимое, требование об удалении персональных данных,
инцидент безопасности, иные документированные moderation grounds.

**Это исключение не скрывается от пользователей.** Скрытая возможность удаления
превратила бы главное обещание в ложь; раскрытая и журналируемая — наоборот,
сильнее обещания, которое никто не может проверить. Никакого скрытого
backdoor-delete в системе нет: каждый маршрут, удаляющий содержимое, назван
ниже, и тест `test_every_removal_route_is_named_in_the_documentation` этого
требует.

### Кто может

Только owner/admin. Полномочие читается из учётной записи
(`account_auth.find_active_user(...).is_owner`), а не из того, что прислал
клиент.

### Две операции, намеренно неравные по силе

| Операция | Что происходит | Когда |
| --- | --- | --- |
| `moderation_removal` (по умолчанию) | Объект перестаёт показываться, на его месте — tombstone. Сохранённое содержимое остаётся в хранилище для записи | Любое документированное основание |
| `hard_erasure` | Содержимое действительно стирается: `text`, `hashtags`, `attachments`, `object_snapshot` очищаются, ставится `content_erased` | Только `legal_request`, `privacy_request`, `illegal_content`, `security_incident` |

Нарушение правил сообщества отвечается tombstone, а не стиранием: попытка
`hard_erasure` с кодом `moderation_policy` даёт `400`.

**Даже при hard erasure сохраняется минимальный non-content audit record** —
кто, когда, почему и SHA-256 отпечаток стёртого. Требование об удалении
выполняется полностью, но факт и предмет удаления остаются доказуемыми.

### Tombstone

- Публикация: `Публикация удалена администрацией`
- Комментарий: `Комментарий удалён администрацией`

Исходное содержимое в tombstone не передаётся никому. Удалённый комментарий
остаётся в треде как tombstone: читатель, видящий ответ в пустоту, узнаёт
меньше, чем читатель, которому сказали, что запись удалена. Удалённая
публикация видна как tombstone **на собственной стене автора** — автор вправе
знать, что его публикацию сняли, — и не показывается в Recommendation, в
поиске и в чужом просмотре этой стены.

### Обязательные основания

`reason_code` — закрытый набор, чтобы журнал читался как данные:

| Код | Значение | Допускает hard erasure |
| --- | --- | --- |
| `legal_request` | Законное требование или решение суда | да |
| `privacy_request` | Требование об удалении персональных данных | да |
| `illegal_content` | Незаконное или опасное содержимое | да |
| `security_incident` | Инцидент безопасности | да |
| `moderation_policy` | Нарушение правил сообщества | нет |

`reason` — человекочитаемое основание, не короче 8 символов, обязательно.
Без любого из двух — `400`, и ничего не удаляется.

### Audit record

Пишется **до** того, как объект будет изменён: удаление, прерванное на
середине, всё равно оставляет след. Хранится в `audit_log`, только растёт.

Каждая запись содержит минимум:

| Поле | Что это |
| --- | --- |
| `target_type`, `target_id` | Объект |
| `author_profile_id` | Оригинальный автор |
| `actor`, `ai_agent_id`, `actor_chain` | Кто выполнил |
| `authority_user_id`, `authority_user_uuid` | Чьим полномочием |
| `occurred_at_utc` | Когда |
| `reason_code`, `reason_label`, `reason` | Код и человекочитаемое основание |
| `source` | `owner_ui` / `owner_api` / `ai_assisted` / `moderation_queue` |
| `content_hash`, `object_version`, `content_length`, `attachment_count` | Отпечаток и версия удалённого объекта |
| `operation` | `moderation_removal` или `hard_erasure` |
| `audit_id`, `correlation_id` | Идентификатор записи и связь с обращением |

**Пользователь не может удалить audit record.** В модуле нет ни одной операции,
которая убирает запись из `audit_log`, и нет соответствующего маршрута;
`test_nothing_in_the_module_removes_an_audit_entry` это фиксирует.

Модерация по жалобе идёт **тем же путём**: `moderate_social_report(action="remove")`
вызывает тот же `_apply_removal` с `source="moderation_queue"`,
`reason_code="moderation_policy"` и `correlation_id` = идентификатор жалобы.
Один путь удаления — один журнал.

### AI

ИИ **не получает автономного права уничтожать публикации.**

Если owner просит ИИ удалить объект:

1. ИИ распознаёт это как administrative erasure и вызывает
   `preview_owner_removal` / `GET /api/community/v2/owner/removal-preview`;
2. показывает, **какой объект и почему** будет удалён (автор, дата, отпечаток,
   доступные коды оснований) — превью ничего не меняет;
3. действие исполняется только с authenticated owner authority: вызов в любом
   случае аутентифицирован как владелец, `actor="ai"` без прав владельца — это
   `403`;
4. сохраняется тот же audit trail;
5. `actor_chain` показывает, что команда исходила от владельца и была исполнена
   через ИИ: `["owner:<id>", "ai:<agent>"]`.

**ИИ никогда не записывается как владелец**: во главе цепочки всегда
`owner:<id>`, а `authority_user_id` — идентификатор владельца.

## 3. Очистка базы данных

Полная очистка Development/test database — отдельная maintenance operation над
хранилищем целиком. Это **не** пользовательский delete-flow и не способ убрать
одну публикацию.

**Production database нельзя очищать этим пользовательским механизмом.**
Маршруты раздела 2 работают с отдельными объектами, требуют owner-полномочия и
основания и всегда пишут журнал; никакой из них не сбрасывает хранилище.

## 4. Маршруты

| Маршрут | Назначение |
| --- | --- |
| `POST /api/community/v2/owner/remove` | Административное удаление (owner-only, обязательны `reason_code` и `reason`) |
| `GET /api/community/v2/owner/removal-preview` | Что будет удалено, без изменений |
| `GET /api/community/v2/owner/audit` | Журнал удалений, только чтение, owner-only |
| `POST /api/community/v2/posts/<id>/delete` | Отказ автору (`403`); для чужого объекта — moderation removal владельцем |
| `POST /api/community/v2/comments/<id>/delete` | То же для комментария |
| `POST /api/community/v2/moderation/<report_id>` | Решение по жалобе; `action=remove` идёт тем же audited путём |

## 5. Как это выражено в продукте

- **Сервер отказывает.** Правило проверяется в `delete_social_post` и
  `delete_social_comment`, а не только скрыто в интерфейсе: прямой вызов API
  проходит через ту же проверку.
- **Контрола нет.** Из карточки публикации и из комментария убраны кнопки
  удаления. Интерфейс не предлагает того, в чём сервер откажет.
- **Проекции честны.** `can_delete` больше никогда не `true`; рядом идут
  `is_author`, `permanent` и `removed`.
- **Пользователь предупреждён до публикации.** Под редактором стоит короткая
  ненавязчивая строка `permanence_notice`, приходящая с сервера — один источник
  формулировки. На своих публикациях стоит знак `∞`.
