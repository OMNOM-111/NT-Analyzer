# Как не перепутать версии StratForge

Используются три однозначные подписи:

| Подпись | Что это | Как открыть |
|---|---|---|
| `РАЗРАБОТКА` / `DEV` | Текущий локальный код и локальные данные только для доработки | `START-DEVELOPMENT.cmd` |
| `ПРЕДРЕЛИЗ` / `CANARY` | Серверная проверка нового релиза для явно выбранных установок | Отдельной кнопки нет; назначает владелец при controlled rollout |
| `СТАБИЛЬНАЯ` / `STABLE` | Готовая серверная версия для пользователей | `OPEN-SERVER.cmd` или `https://app.stratforges.com/ui/` |

Термин «оригинал» не используется: он не говорит, готова ли сборка. Возле
названия приложения всегда показываются фактически полученные от backend
версия, канал и дата сборки, например `v0.9.0-dev.1 · DEV · от 21.07.2026`.

`start.ps1` и `START-DEVELOPMENT.cmd` технически запрещены для Production и
всегда показывают предупреждение о локальном Development. `OPEN-SERVER.cmd`
ничего локально не запускает: сначала проверяет `/api/runtime/env`, печатает
фактические версию и канал, предупреждает, если сервер ещё DEV/CANARY, и только
потом открывает canonical URL. Версия Production задаётся при публикации через
защищённые переменные окружения; сервер не стартует, если version/channel/date
отсутствуют или противоречат окружению.

Правило именования:

- `1.2.3` — стабильный релиз;
- `1.3.0-rc.1` — canary/предрелиз;
- `1.3.0-dev.4` — незавершённая локальная разработка.

Проверяемая сборка новой локальной Server-версии из чистого commit выполняется
одной командой: `py -3 tools/release_candidate.py --server-only`. Полный путь
того же артефакта через canary в Production описан в
`docs/PRODUCTION_RELEASE_WORKFLOW.md`.
